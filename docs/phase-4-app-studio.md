# المرحلة الرابعة: AI App Studio

**معيار القبول:** «إنشاء تطبيقات من نطاق محدد، واختبارها ونشرها بأمان ضمن الحدود المعلنة».
يتحقق منه `tests/test_studio.py`.

```
قالب ──▶ نسخة عمل ◀── المُنشئ الذكي (يعدّل الملفات فقط)
            │
       إصدار (لقطة ثابتة + نتائج الفحوص)
            │
   ┌────────┴─────────┐
 معاينة (فورًا)     طلب إنتاج ──▶ موافقة من يملك apps.deploy ──▶ موقع منشور
                                                    │
                                     رجوع = نشر إصدار سابق بنفس الموافقة
```

## النطاق المحدد: قالب «تطبيق ويب ثابت»

HTML وCSS وJavaScript تعمل في المتصفح: صفحات تعريفية، كتالوجات، حاسبات، نماذج.
- القالب يبدأ جاهزًا للعربية (RTL)، مع **Design Tokens** في متغيرات CSS، ووضع داكن، واحترام تقليل الحركة.
- اسم المشروع يُهرَّب (escape) قبل وضعه في HTML.

**لماذا قالب واحد الآن؟** لأن المنصة تستطيع فحصه بالكامل **دون تشغيل كوده**.
التطبيقات التي فيها كود خادم (API، قاعدة بيانات) تحتاج بيئة تنفيذ معزولة حقيقية (MicroVM مثل Firecracker أو gVisor) قبل السماح بها، كما ينص المخطط.
هذه البيئة لم تُبنَ بعد، ولم أضع بديلًا ضعيفًا يوحي بالأمان.

## الفحوص (تعمل على كل إصدار)

| الفحص | يفشل عند | يحذّر عند |
|---|---|---|
| entry_point | غياب index.html | |
| file_types | نوع ملف غير مسموح (exe مثلًا) | |
| secrets | مفاتيح API أو مفاتيح خاصة أو tokens داخل الملفات | |
| html_structure | `<html>` بلا lang | صفحة عربية بلا dir=rtl، أو غياب viewport أو title |
| local_references | رابط أو src يشير لملف غير موجود | |
| javascript_syntax | خطأ نحوي، عبر `node --check` الذي يحلل الكود ولا ينفذه | |
| accessibility | | صورة بلا نص بديل |
| external_scripts / insecure_links | | سكربت من موقع خارجي، أو رابط http |

**الإصدار الذي فيه أي فحص فاشل لا يمكن نشره للإنتاج.** المعاينة مسموحة دائمًا لرؤية العمل.

## المُنشئ الذكي

- **الأدوات المتاحة له فقط:** list_files وread_file وwrite_file وdelete_file وrun_checks.
- **لا يستطيع إنشاء إصدار ولا النشر:** هذه قرارات المستخدم.
- **لا يخرج عن المشروع:** كل مسار يمر عبر `clean_path`، فيُرفض `..` والمسارات المطلقة والملفات المخفية (`.env`).
- **التعديل كما يطلب المخطط:** يقرأ الملفات المتأثرة ويعدّل ما يلزم فقط، ثم يشغّل الفحوص.
  التغييرات في نسخة العمل، ويراها المستخدم كفروقات (diff) قبل إنشاء الإصدار، ويستطيع الرجوع لأي إصدار.
- **التشغيل:** `claude-opus-5-5` بـ effort عالٍ، مع البث (streaming) و`eager_input_streaming` لأنه يكتب ملفات كاملة.
  كل مُدخل أداة يُتحقق منه قبل التنفيذ، واستدعاء أداة انقطع بسبب حد التوكنات لا يُنفَّذ أبدًا.
- **الحدود:** نفس منظومة المرحلة الثالثة (ميزانية المؤسسة، مفتاح الإيقاف، 8 خطوات لكل رسالة، تسجيل التكلفة).

## التخزين والإصدارات

- **تخزين بحسب المحتوى:** كل ملف يُخزن مرة واحدة بالـ SHA-256 الخاص به، والإصدار قائمة `{مسار: hash}`.
- **الإصدارات ثابتة:** في PostgreSQL لا يملك دور الـ API عليها UPDATE ولا DELETE.
- **التصدير:** ZIP لأي إصدار. العميل يملك كوده ويأخذه أينما شاء.
- **الحدود:** 200 ملف، 512KB للملف، 5MB للمشروع، عمق 6 مجلدات.

## النشر والعزل

- **المعاينة:** رابط خاص غير قابل للتخمين لكل نشر.
- **الإنتاج:** رابط ثابت للمشروع يُعاد توجيهه عند كل نشر أو رجوع.
  طلب الإنتاج منفصل عن الموافقة عليه: دور developer يطلب، ومن يملك `apps.deploy` يوافق أو يرفض. لا يُسمح إلا بطلب معلّق واحد.
- **إيقاف فوري:** `/offline` يوقف كل نشرات المشروع.
- **العزل:** المواقع تُخدَم بـ `Content-Security-Policy: sandbox`، فتعمل صفحاتها بأصل معزول ولا تصل سكربتاتها إلى cookies المنصة أو تخزينها.
  ومع ذلك **في الإنتاج يجب خدمة المواقع من نطاق منفصل** (`NOVARA_SITES_BASE_URL`)، وهذه طبقة إضافية وليست بديلًا.
- **جدول التوجيه العام:** `app_site_routes` بلا RLS عمدًا، لأن خدمة موقع عام تتطلب معرفة مؤسسته أولًا.
  هو يحوي بيانات توجيه فقط، ويُقرأ المحتوى بعد ربط المؤسسة.

## ربط الموقع ببيانات الأعمال (مفاتيح البيانات)

الموقع المنشور يقرأ كتالوج المؤسسة بمفتاح بيانات للقراءة فقط، يُنشأ من تبويب «البيانات» في صفحة المشروع:

```js
const res = await fetch("https://app.example.com/api/v1/public/catalog", { headers: { "X-Novara-Key": "nvpk_..." } });
const { currency, products } = await res.json();   // name, sku, price, price_with_tax, tax_rate, unit, (available)
```

- **المفتاح علني بطبيعته** لأنه في شيفرة الموقع، لذلك لا يقرأ إلا ما اختار المالك نشره:
  `catalog` (المنتجات النشطة وأسعارها قبل الضريبة وبعدها) و`availability` (هل الصنف متوفر بعد ما تحجزه أوامر البيع المؤكدة).
  التكاليف والكميات الفعلية والعملاء والفواتير لا تُعرض أبدًا.
- **إنشاؤه قرار نشر:** يتطلب `apps.deploy`، ولا يُنشر إلا ما يقرؤه المنشئ نفسه (`products.read`، و`inventory.read` للتوفر).
  من يملك `apps.write` يستطيع إيقافه فورًا، وكلا الأمرين في سجل التدقيق.
- **التخزين:** بصمة SHA-256 فقط، والمفتاح يظهر مرة واحدة عند إنشائه. معرفة مؤسسة المفتاح في PostgreSQL تمر عبر
  دالة `SECURITY DEFINER` (`app_data_key_org`) لا تكشف شيئًا آخر، ثم تُقرأ البيانات تحت RLS المؤسسة.
- **CORS مفتوح** (`*`) لأن صفحات المواقع تعمل بأصل معزول (sandbox) لا اسم له، والإجابة تُخزَّن مؤقتًا دقيقة واحدة.
  تاريخ آخر استخدام يُحدَّث مرة في الدقيقة على الأكثر مهما كثرت الزيارات.

### طلبات الشراء من الموقع (نطاق `orders`)

مفتاح بنطاق `orders` يتيح للموقع إرسال طلب زائر:

```js
await fetch("https://app.example.com/api/v1/public/orders", {
  method: "POST",
  headers: { "X-Novara-Key": "nvpk_...", "Content-Type": "application/json" },
  body: JSON.stringify({ name, email, phone, note, lines: [{ product_id, quantity: 2 }] }),
});   // 201 { reference: "WEB-2026-00001", total, currency }
```

- **لا شيء يُحجز أو يُرحَّل:** الطلب ينتظر في «أوامر البيع» حتى يحوّله شخص إلى عرض سعر (يُعثر على العميل ببريده أو يُنشأ) أو يتجاهله. وصول الطلب حدث `web_order.received` يمكن أن يطلق سير عمل (إشعار فريق المبيعات مثلاً).
- **الأسعار من الكتالوج في الخادم دائماً،** ولا يُقبل أي سعر من الموقع. المنتج المؤرشف أو من مؤسسة أخرى مرفوض.
- **الحماية من الإساءة:** يلزم بريد أو هاتف للرد. حقل مخفي `website` يتركه الناس فارغاً ويملؤه الروبوت، فيُرد عليه بالقبول ولا يُحفظ شيء. حد 30 طلباً في الساعة لكل مفتاح و5 في عشر دقائق لكل عنوان IP (429). حدود لطول كل حقل ولعدد البنود (50) وللكمية.
- **إنشاء المفتاح بهذا النطاق** يتطلب `sales.write` إضافة إلى `apps.deploy`، والتحويل إلى عرض سعر يتطلب `sales.write` و`customers.write`.

### الحجوزات من الموقع (نطاق `bookings`)

مفتاح بنطاق `bookings` يتيح للموقع عرض الخدمات والأوقات المتاحة وطلب موعد:

```js
const h = { "X-Novara-Key": "nvpk_..." };
const { services, timezone } = await (await fetch("https://app.example.com/api/v1/public/booking-services", { headers: h })).json();
const { times } = await (await fetch(`https://app.example.com/api/v1/public/free-times?service=${id}&day=2026-11-01`, { headers: h })).json();
await fetch("https://app.example.com/api/v1/public/bookings", {
  method: "POST",
  headers: { ...h, "Content-Type": "application/json" },
  body: JSON.stringify({ service_id: id, starts_at: times[0], name, email, phone, note }),
});   // 201 { reference: "BK-2026-00001", status: "requested" }
```

- **الطلب يحجز وقته** حتى يؤكده الفريق أو يرفضه من صفحة «الحجوزات»، ويُشعَر من يملك `bookings.manage` بوصوله. وصوله حدث `booking.requested` وتأكيد أي حجز حدث `booking.confirmed`.
- **الموقع لا يحجز إلا وقتاً من القائمة:** داخل ساعات العمل، غير محجوز، بعد المهلة (ساعتان افتراضياً) وقبل نهاية نافذة الحجز (60 يوماً). الوقت المأخوذ للتو يُرد عليه بـ 409، وأي وقت آخر بـ 422.
- **الحماية من الإساءة** كما في الطلبات: بريد أو هاتف إلزامي، والحقل المخفي `website`، و30 طلباً في الساعة لكل مفتاح و5 في عشر دقائق لكل عنوان.
- **إنشاء المفتاح بهذا النطاق** يتطلب `bookings.manage` إضافة إلى `apps.deploy`.

## الأدوار

| الدور | يستطيع |
|---|---|
| developer | إنشاء المشاريع، استخدام المُنشئ الذكي، إنشاء الإصدارات، نشر المعاينات، **طلب** الإنتاج |
| owner / admin | كل ما سبق، والموافقة على الإنتاج أو رفضه، والإيقاف |

## ما لم يُنجز بعد

- **بيئة التنفيذ المعزولة (MicroVM)** لقوالب فيها كود خادم. هذا الشرط الأساسي قبل توسيع القوالب.
- **نطاقات مخصصة للعملاء** (custom domains) وشهادات TLS.
- **اختبارات واجهة حقيقية في متصفح** (Playwright) للتطبيقات المولّدة. الفحوص الحالية ثابتة (static) فقط.
- **الدفع من الموقع:** الموقع يرسل طلب شراء أو طلب حجز ينتظر الفريق، ولا يوجد دفع إلكتروني بعد.
- **التحقق البشري (CAPTCHA)** للطلبات العامة: الحماية الحالية حقل مخفي وحدود للمعدل.

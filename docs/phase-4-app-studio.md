# المرحلة الرابعة: AI App Studio

**معيار القبول:** «إنشاء تطبيقات من نطاق محدد، واختبارها ونشرها بأمان ضمن الحدود المعلنة».
يتحقق منه `tests/test_studio.py`.

```
قالب ──▶ نسخة عمل ◀── المُنشئ الذكي (يعدّل الملفات فقط)
            │
       إصدار (لقطة ثابتة + نتائج الفحوص)
            │
   ┌────────┴─────────┐
 معاينة (فورًا)     طلب إنتاج ──▶ موافقة من يملك apps.deploy ──▶ موقع منشور
                                                    │
                                     رجوع = نشر إصدار سابق بنفس الموافقة
```

## النطاق المحدد: قالب «تطبيق ويب ثابت»

HTML وCSS وJavaScript تعمل في المتصفح: صفحات تعريفية، كتالوجات، حاسبات، نماذج.
- القالب يبدأ جاهزًا للعربية (RTL)، مع **Design Tokens** في متغيرات CSS، ووضع داكن، واحترام تقليل الحركة.
- اسم المشروع يُهرَّب (escape) قبل وضعه في HTML.

قالب **«متجر»** مبني على النوع نفسه: صفحة منتجات من كتالوج المؤسسة، وسلة، ونموذج طلب بالتحقق من البشر، وملف
`config.js` يحمل عنوان الخادم ومفتاح البيانات. ينشئه الإعداد الأول للمؤسسة جاهزاً ومنشوراً (انظر المرحلة الأولى)،
ويُعدَّل بعدها كأي مشروع.

**لماذا نوع واحد من القوالب الآن؟** لأن المنصة تستطيع فحصه بالكامل دون تشغيل كوده على الخادم: كوده يعمل في متصفح الزائر، والفحص في المتصفح (أدناه) يشغّله في Chromium معزول عن الشبكة.
التطبيقات التي فيها كود خادم (API، قاعدة بيانات) تحتاج بيئة تنفيذ معزولة حقيقية (MicroVM مثل Firecracker أو gVisor) قبل السماح بها، كما ينص المخطط.
هذه البيئة لم تُبنَ بعد، ولم أضع بديلًا ضعيفًا يوحي بالأمان.

## الفحوص (تعمل على كل إصدار)

| الفحص | يفشل عند | يحذّر عند |
|---|---|---|
| entry_point | غياب index.html | |
| file_types | نوع ملف غير مسموح (exe مثلًا) | |
| secrets | مفاتيح API أو مفاتيح خاصة أو tokens داخل الملفات | |
| html_structure | `<html>` بلا lang | صفحة عربية بلا dir=rtl، أو غياب viewport أو title |
| local_references | رابط أو src يشير لملف غير موجود | |
| javascript_syntax | خطأ نحوي، عبر `node --check` الذي يحلل الكود ولا ينفذه | |
| accessibility | | صورة بلا نص بديل |
| external_scripts / insecure_links | | سكربت من موقع خارجي، أو رابط http |
| browser_errors | خطأ JavaScript غير معالَج عند فتح الصفحة | الخطأ نفسه إن جاء بعد طلب بيانات حية من NOVARA (لا تُحمَّل أثناء الفحص) |
| browser_render | صفحة فارغة، أو لم تكتمل خلال 10 ثوانٍ | صورة محلية لا تظهر |
| browser_requests | الصفحة تطلب ملفاً غير موجود (حتى من داخل JavaScript) | طلب لموقع آخر (يُمنع ولا يُفحص) |
| browser_layout / browser_console | | الصفحة أعرض من شاشة الهاتف، أو رسالة خطأ في الـ console |

**الإصدار الذي فيه أي فحص فاشل لا يمكن نشره للإنتاج.** المعاينة مسموحة دائمًا لرؤية العمل.

### الفحص في متصفح حقيقي

كل صفحة HTML (حتى 10 صفحات) تُفتح في Chromium بلا واجهة على شاشة كبيرة (1280×800) وعلى هاتف (390×844)، ويُنفَّذ كودها كما عند الزائر. هذا الفحص الوحيد الذي يشغّل كود المشروع، لذلك:

- يعمل في عملية Node.js منفصلة (`novara/studio/browser_check.cjs`) بمهلة وبيئة شبه فارغة.
- **لا يصل شيء إلى الشبكة:** كل طلب تجيبه ملفات الإصدار نفسها، وطلبات المواقع الأخرى تُرفض داخل المتصفح. وكجدار ثانٍ يعمل Chromium بوكيل (proxy) لا يرد وبمحلّل أسماء لا يجد أي مضيف، فلا يصل WebSocket ولا عامل (Worker) ولا إطار إلى أي عنوان، ولا حتى عنوان الخادم نفسه (`127.0.0.1`). الاختبار يشغّل خادماً محلياً ويتحقق أنه لم يتلقَّ طلباً واحداً. عمّال الخدمة (service workers) ممنوعون، والنوافذ المنبثقة والتنزيلات تُغلق.
- تُحفظ صورتان للصفحة الرئيسية لكل إصدار (شاشة كبيرة وهاتف) تظهران في تبويب «الإصدارات».
- المُنشئ الذكي يرى نتائج هذا الفحص أيضاً حين يشغّل الفحوص أثناء عمله، فيصلح الخطأ قبل أن يراه المستخدم.
- فحص الإصدار يستغرق نحو ثانيتين لموقع صغير.

| المتغير | الغرض |
|---|---|
| `NOVARA_BROWSER_CHECKS` | `on` أو `off`. يعمل افتراضياً في التطوير، ومعطل افتراضياً في الإنتاج |
| `NOVARA_BROWSER_SANDBOX` | تشغيل Chromium بعزله الخاص (sandbox). `true` افتراضياً في الإنتاج: يحتاج أن يعمل الخادم بغير root ومع user namespaces، وإلا ظهر تنبيه بأن الفحص لم يعمل. لا تضبطه على `false` في الإنتاج إلا على جهاز منفصل للفحوص |
| `NOVARA_BROWSER_NODE_PATH` | مكان حزمة `playwright` (افتراضياً `NODE_PATH`). التثبيت: `npm install playwright` ثم `npx playwright install --with-deps chromium` |

إن لم يكن Node.js أو Playwright مثبتاً، أو لم يبدأ Chromium، يظهر تنبيه بذلك ولا يُمنع النشر، كما في فحص `node --check`.

## المُنشئ الذكي

- **الأدوات المتاحة له فقط:** list_files وread_file وwrite_file وdelete_file وrun_checks.
- **لا يستطيع إنشاء إصدار ولا النشر:** هذه قرارات المستخدم.
- **لا يخرج عن المشروع:** كل مسار يمر عبر `clean_path`، فيُرفض `..` والمسارات المطلقة والملفات المخفية (`.env`).
- **التعديل كما يطلب المخطط:** يقرأ الملفات المتأثرة ويعدّل ما يلزم فقط، ثم يشغّل الفحوص.
  التغييرات في نسخة العمل، ويراها المستخدم كفروقات (diff) قبل إنشاء الإصدار، ويستطيع الرجوع لأي إصدار.
- **التشغيل:** `claude-opus-5-5` بـ effort عالٍ، مع البث (streaming) و`eager_input_streaming` لأنه يكتب ملفات كاملة.
  كل مُدخل أداة يُتحقق منه قبل التنفيذ، واستدعاء أداة انقطع بسبب حد التوكنات لا يُنفَّذ أبدًا.
- **الحدود:** نفس منظومة المرحلة الثالثة (ميزانية المؤسسة، مفتاح الإيقاف، 8 خطوات لكل رسالة، تسجيل التكلفة).

## التخزين والإصدارات

- **تخزين بحسب المحتوى:** كل ملف يُخزن مرة واحدة بالـ SHA-256 الخاص به، والإصدار قائمة `{مسار: hash}`.
- **الإصدارات ثابتة:** في PostgreSQL لا يملك دور الـ API عليها UPDATE ولا DELETE.
- **التصدير:** ZIP لأي إصدار. العميل يملك كوده ويأخذه أينما شاء.
- **الحدود:** 200 ملف، 512KB للملف، 5MB للمشروع، عمق 6 مجلدات.

## النشر والعزل

- **المعاينة:** رابط خاص غير قابل للتخمين لكل نشر.
- **الإنتاج:** رابط ثابت للمشروع يُعاد توجيهه عند كل نشر أو رجوع.
  طلب الإنتاج منفصل عن الموافقة عليه: دور developer يطلب، ومن يملك `apps.deploy` يوافق أو يرفض. لا يُسمح إلا بطلب معلّق واحد.
- **إيقاف فوري:** `/offline` يوقف كل نشرات المشروع.
- **العزل:** المواقع تُخدَم بـ `Content-Security-Policy: sandbox`، فتعمل صفحاتها بأصل معزول ولا تصل سكربتاتها إلى cookies المنصة أو تخزينها.
  ومع ذلك **في الإنتاج يجب خدمة المواقع من نطاق منفصل** (`NOVARA_SITES_BASE_URL`)، وهذه طبقة إضافية وليست بديلًا.
- **جدول التوجيه العام:** `app_site_routes` بلا RLS عمدًا، لأن خدمة موقع عام تتطلب معرفة مؤسسته أولًا.
  هو يحوي بيانات توجيه فقط، ويُقرأ المحتوى بعد ربط المؤسسة.

## ربط الموقع ببيانات الأعمال (مفاتيح البيانات)

الموقع المنشور يقرأ كتالوج المؤسسة بمفتاح بيانات للقراءة فقط، يُنشأ من تبويب «البيانات» في صفحة المشروع:

```js
const res = await fetch("https://app.example.com/api/v1/public/catalog", { headers: { "X-Novara-Key": "nvpk_..." } });
const { currency, products } = await res.json();   // name, sku, price, price_with_tax, tax_rate, unit, (available)
```

- **المفتاح علني بطبيعته** لأنه في شيفرة الموقع، لذلك لا يقرأ إلا ما اختار المالك نشره:
  `catalog` (المنتجات النشطة وأسعارها قبل الضريبة وبعدها) و`availability` (هل الصنف متوفر بعد ما تحجزه أوامر البيع المؤكدة).
  التكاليف والكميات الفعلية والعملاء والفواتير لا تُعرض أبدًا.
- **إنشاؤه قرار نشر:** يتطلب `apps.deploy`، ولا يُنشر إلا ما يقرؤه المنشئ نفسه (`products.read`، و`inventory.read` للتوفر).
  من يملك `apps.write` يستطيع إيقافه فورًا، وكلا الأمرين في سجل التدقيق.
- **التخزين:** بصمة SHA-256 فقط، والمفتاح يظهر مرة واحدة عند إنشائه. معرفة مؤسسة المفتاح في PostgreSQL تمر عبر
  دالة `SECURITY DEFINER` (`app_data_key_org`) لا تكشف شيئًا آخر، ثم تُقرأ البيانات تحت RLS المؤسسة.
- **CORS مفتوح** (`*`) لأن صفحات المواقع تعمل بأصل معزول (sandbox) لا اسم له، والإجابة تُخزَّن مؤقتًا دقيقة واحدة.
  تاريخ آخر استخدام يُحدَّث مرة في الدقيقة على الأكثر مهما كثرت الزيارات.

### طلبات الشراء من الموقع (نطاق `orders`)

مفتاح بنطاق `orders` يتيح للموقع إرسال طلب زائر:

```js
await fetch("https://app.example.com/api/v1/public/orders", {
  method: "POST",
  headers: { "X-Novara-Key": "nvpk_...", "Content-Type": "application/json" },
  body: JSON.stringify({ name, email, phone, note, lines: [{ product_id, quantity: 2 }] }),
});   // 201 { reference: "WEB-2026-00001", total, currency }
```

- **لا شيء يُحجز أو يُرحَّل:** الطلب ينتظر في «أوامر البيع» حتى يحوّله شخص إلى عرض سعر (يُعثر على العميل ببريده أو يُنشأ) أو يتجاهله. وصول الطلب حدث `web_order.received` يمكن أن يطلق سير عمل (إشعار فريق المبيعات مثلاً).
- **الأسعار من الكتالوج في الخادم دائماً،** ولا يُقبل أي سعر من الموقع. المنتج المؤرشف أو من مؤسسة أخرى مرفوض.
- **الحماية من الإساءة:** يلزم بريد أو هاتف للرد. التحقق من أن الطلب يرسله شخص (انظر «التحقق من البشر» أدناه). حقل مخفي `website` يتركه الناس فارغاً ويملؤه الروبوت، فيُرد عليه بالقبول ولا يُحفظ شيء. حد 30 طلباً في الساعة لكل مفتاح و5 في عشر دقائق لكل عنوان IP (429). حدود لطول كل حقل ولعدد البنود (50) وللكمية.
- **إنشاء المفتاح بهذا النطاق** يتطلب `sales.write` إضافة إلى `apps.deploy`، والتحويل إلى عرض سعر يتطلب `sales.write` و`customers.write`.

### الدفع في الموقع (نطاق `checkout`)

مفتاح بنطاق `checkout` (يشمل `orders`) يتيح للزائر أن يدفع عند الطلب، عبر مزوّد الدفع الإلكتروني الذي اختارته المؤسسة (Stripe أو ميسّر أو هايبر باي):

```js
const order = await (await fetch("https://app.example.com/api/v1/public/orders", {
  method: "POST",
  headers: { "X-Novara-Key": "nvpk_...", "Content-Type": "application/json" },
  body: JSON.stringify({ name, email, phone, note, lines: [{ product_id, quantity: 2 }], pay: true }),
})).json();   // 201 { reference, total, currency, payment_url }
window.location.href = order.payment_url;
```

- **قبل الدفع لا يُرحَّل شيء:** الطلب «بانتظار الدفع» في «أوامر البيع»، ورابط الدفع له وحده بإجماليه وبعملة المؤسسة، ويصلح ساعتين.
- **حين يؤكد المزوّد الدفع** (بالطريقة نفسها التي تُؤكَّد بها روابط الفواتير: استدعاء موقّع أو جواب واجهة المزوّد) يصبح الطلب فاتورة العميل: يُعثر عليه ببريده أو يُنشأ، وتُبنى الفاتورة بالأسعار والضرائب التي أُخذ بها الطلب، وتُرحَّل بتاريخ الدفع وتُسجَّل دفعتها في حساب «مدفوعات إلكترونية قيد التسوية»، وتصدر فاتورتها الإلكترونية المبسطة إن كانت الفوترة الإلكترونية مفعّلة (يرسلها العامل الخلفي إلى الهيئة)، ويُبلَّغ فريق المبيعات ليجهّز الطلب. كل ذلك في معاملة واحدة، ومرة واحدة مهما تكرر التأكيد.
- **إن لم يمكن ذلك** (حُوّل الطلب أو تُجوهل قبل وصول المال، أو اختلف المبلغ، أو الفترة مقفلة) لا يُرحَّل شيء، ويصبح الرابط «لم تُسجَّل» ويُبلَّغ فريق المبيعات ليرد المبلغ أو يسجله يدوياً. تحويل الطلب أو تجاهله وهو بانتظار الدفع يغلق رابطه.
- **إنشاء المفتاح بهذا النطاق** يتطلب، إضافة إلى صلاحيات `orders`، `customers.write` و`invoices.post` و`payments.write`، لأن الطلب المدفوع يصبح فاتورة مرحّلة ودفعة. المفتاح بلا هذا النطاق يُرفض طلبه بالدفع (403)، والمؤسسة بلا مزوّد دفع ترد بـ 409 ولا يُحفظ الطلب.
- **التسليم** يبقى على الفريق: الفاتورة المدفوعة لا تُخرج المخزون، فيسلّم الفريق ما طُلب كما يفعل مع الطلبات الأخرى.

### الحجوزات من الموقع (نطاق `bookings`)

مفتاح بنطاق `bookings` يتيح للموقع عرض الخدمات والأوقات المتاحة وطلب موعد:

```js
const h = { "X-Novara-Key": "nvpk_..." };
const { services, timezone } = await (await fetch("https://app.example.com/api/v1/public/booking-services", { headers: h })).json();
const { times } = await (await fetch(`https://app.example.com/api/v1/public/free-times?service=${id}&day=2026-11-01`, { headers: h })).json();
await fetch("https://app.example.com/api/v1/public/bookings", {
  method: "POST",
  headers: { ...h, "Content-Type": "application/json" },
  body: JSON.stringify({ service_id: id, starts_at: times[0], name, email, phone, note }),
});   // 201 { reference: "BK-2026-00001", status: "requested" }
```

- **الطلب يحجز وقته** حتى يؤكده الفريق أو يرفضه من صفحة «الحجوزات»، ويُشعَر من يملك `bookings.manage` بوصوله. وصوله حدث `booking.requested` وتأكيد أي حجز حدث `booking.confirmed`.
- **الموقع لا يحجز إلا وقتاً من القائمة:** داخل ساعات العمل، غير محجوز، بعد المهلة (ساعتان افتراضياً) وقبل نهاية نافذة الحجز (60 يوماً). الوقت المأخوذ للتو يُرد عليه بـ 409، وأي وقت آخر بـ 422.
- **الحماية من الإساءة** كما في الطلبات: بريد أو هاتف إلزامي، والتحقق من البشر، والحقل المخفي `website`، و30 طلباً في الساعة لكل مفتاح و5 في عشر دقائق لكل عنوان.
- **إنشاء المفتاح بهذا النطاق** يتطلب `bookings.manage` إضافة إلى `apps.deploy`.

## التحقق من البشر (بديل CAPTCHA)

طلبات الشراء والحجز من الموقع تحمل «إثبات عمل» (proof of work) بدل الألغاز، وبلا أي خدمة خارجية ولا تتبع للزائر (`studio/proof.py`):

1. صفحة الموقع تطلب تحدياً: `GET /api/v1/public/challenge` بالمفتاح. التحدي موقّع بـ HMAC ومربوط بالمفتاح وبالصعوبة وبوقت انتهاء (5 دقائق)، فلا يُحفظ شيء عند إصداره.
2. المتصفح يبحث عن رقم n يجعل `SHA-256("<التحدي>:<n>")` يبدأ بـ 16 بتاً صفرية (نحو 65 ألف محاولة: ثانية تقريباً على الهاتف). السكربت `GET /api/v1/public/proof.js` يعرّف `novaraProof(base, key)` ويحسب SHA-256 بنفسه، فيعمل داخل صندوق الموقع المعزول.
3. الطلب يحمل `"proof": {"challenge": ..., "nonce": ...}`. الخادم يتحقق من التوقيع والمفتاح وعدم الانتهاء والحل، ثم يسجّل التحدي مستخدَماً حتى ينتهي، فيعمل مرة واحدة.

العنوان الذي يكرر الطلبات يحصل على تحديات أصعب (بت إضافي، أي ضعف العمل، لكل طلبين في عشر دقائق، حتى 20 بتاً). الطلب المرفوض يأتي بـ 403 مع السبب ورؤوس CORS ليقرأها سكربت الموقع. التحقق مفعّل في كل مفتاح جديد فيه الطلبات أو الحجوزات (ويمكن إيقافه عند الإنشاء)، والمفاتيح الأقدم تبقى بدونه حتى تُستبدل، وتظهر في القائمة بشارة «بلا تحقق من البشر». هذا لا يمنع شخصاً مصمماً من إرسال طلبات قليلة بيده، ولذلك تبقى حدود المعدل.

## نطاقات العملاء الخاصة

موقع الإنتاج يمكن أن يُعرض على نطاق المؤسسة نفسها (`studio/domains.py`):

1. من يملك `apps.deploy` يضيف النطاق للمشروع (مثل `www.shop.sa`). يُحفظ بأحرف صغيرة وبصيغة IDNA، فالنطاقات العربية تعمل. تُرفض عناوين IP و`localhost` والأسماء المحجوزة وعناوين المنصة نفسها.
2. يُثبت أنه يملكه بسجل TXT: `_novara-challenge.<النطاق>` قيمته رمز خاص بالنطاق، ويوجّه النطاق إلى خادم المواقع بسجل CNAME (`NOVARA_SITES_CNAME_TARGET`). زر «تحقّق الآن» يبحث عن السجل، وأي فشل في الاستعلام يظهر سببه ولا يُعد خطأ.
3. بعد الإثبات، أي طلب بهذا الاسم في رأس Host يحصل على موقع الإنتاج الحي بنفس رؤوس العزل (sandbox CSP). أي اسم آخر، ومنه عناوين المنصة، يمر إلى المسارات العادية.

يمكن لأكثر من مؤسسة أن تضيف الاسم نفسه ما دام لم يُثبت، والأولى التي تثبته تأخذه (فهرس فريد على الأسماء المثبتة)، فلا يستطيع أحد حجز نطاق غيره بمجرد إضافته. شهادات TLS تصدر عند أول زيارة: Caddy يسأل `GET /api/v1/public/domains/check?domain=...` قبل طلب الشهادة، ولا يجيب بـ 200 إلا لنطاق مثبت موقعه حي (المثال في `infrastructure/deployment/Caddyfile.sites`). الإضافة والإثبات والإزالة في سجل التدقيق.

## الأدوار

| الدور | يستطيع |
|---|---|
| developer | إنشاء المشاريع، استخدام المُنشئ الذكي، إنشاء الإصدارات، نشر المعاينات، **طلب** الإنتاج |
| owner / admin | كل ما سبق، والموافقة على الإنتاج أو رفضه، والإيقاف |

## ما لم يُنجز بعد

- **بيئة التنفيذ المعزولة (MicroVM)** لقوالب فيها كود خادم. هذا الشرط الأساسي قبل توسيع القوالب.
- **اختبارات تفاعل في المتصفح:** الفحص في المتصفح يفتح الصفحات ويرى أخطاءها وشكلها، لكنه لا يضغط الأزرار ولا يملأ النماذج، ولا يحمّل البيانات الحية من NOVARA. ولا تُقاس إمكانية الوصول آلياً (التباين، ترتيب العناوين) بعد.
- **الدفع من الموقع:** مبني لطلبات الشراء (نطاق `checkout` أعلاه)، لا للحجوزات (الحجز ينتظر تأكيد الفريق، ثم يمكن إرسال رابط دفع لفاتورته). ولا سلة محفوظة ولا حسابات للزوار: الموقع يبني السلة بنفسه ويرسلها مرة واحدة. والفاتورة المدفوعة لا تُنشئ أمر بيع ولا تُخرج المخزون.

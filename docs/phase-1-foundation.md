# المرحلة الأولى: الأساس (Phase 1 — Foundation)

هذا ما بُني فعلًا في `services/api`، وكيف يحقق معيار القبول:
**إنشاء مؤسسة، إضافة مستخدمين، تقييد الوصول لبيانات كل مؤسسة، والتحقق باختبارات.**

## كيف يعمل العزل (طبقتان مستقلتان)

**الطبقة 1: التطبيق (`novara/tenancy.py`).** كل نموذج يرث `TenantScoped` يملك `organization_id`.
بعد `bind_tenant(session, org_id)`، الذي يستدعيه `org_context` تلقائيًا بعد التحقق من العضوية:

- كل `SELECT/UPDATE/DELETE`، بما فيها `session.get()` والتحديث الجماعي، يُفلتر تلقائيًا بالمؤسسة.
- السجلات الجديدة تأخذ `organization_id` تلقائيًا، وأي محاولة لكتابة سجل لمؤسسة أخرى أو نقله إليها تُرفض.
- الاستعلام دون مؤسسة محددة **يفشل بخطأ** بدل أن يعيد بيانات كل المؤسسات.
- الوصول المقصود عبر المؤسسات يتطلب `system_scope` صريحًا، فيسهل حصره ومراجعته (يوجد حاليًا في "قائمة مؤسساتي" فقط).

**الطبقة 2: قاعدة البيانات (PostgreSQL RLS).** الـ API يتصل بدور `novara_app` الذي لا يملك الجداول وليس له `BYPASSRLS`.
في بداية كل معاملة تُضبط `app.current_org` و`app.current_user`، والسياسات تمنع رؤية أو كتابة صفوف مؤسسة أخرى
حتى لو تجاوز كود ما فلتر ORM أو نفّذ SQL خامًا. سجل التدقيق لا يملك هذا الدور عليه `UPDATE` ولا `DELETE`.

الاختبارات تثبت الطبقتين. وتعطيل فلتر ORM مؤقتًا يُفشل 7 اختبارات، أي أنها تقيس العزل فعلًا ولا تنجح بالصدفة.

## أمان الحساب

| الحماية | كيف |
|---|---|
| تخمين كلمة المرور | 5 محاولات فاشلة لكل بريد و30 لكل عنوان IP خلال 15 دقيقة، ثم `429` مع `Retry-After`. الدخول الناجح يصفّر عدّاد البريد. |
| روابط البريد | تأكيد البريد (48 ساعة) واستعادة كلمة المرور (ساعة، وحد أقصى 3 رسائل في الساعة) والدعوات (7 أيام). كلها لمرة واحدة، وتُحفظ بصمتها SHA-256 فقط. |
| كشف الحسابات | طلب الاستعادة يردّ بالجواب نفسه دائماً، سواء كان للبريد حساب أم لا. |
| الجلسات بعد تغيير كلمة المرور | الاستعادة تُنهي كل الجلسات. التغيير من صفحة الحساب ينهي الأجهزة الأخرى ويُبقي الجهاز الحالي. |
| التحقق بخطوتين | رموز TOTP (RFC 6238) يرفض الخادم إعادة استخدامها. السر مشفّر في القاعدة بـ AES-256-GCM ومربوط بالمستخدم. رموز الاسترداد العشرة تُحفظ ببصمتها، وكل رمز يعمل مرة واحدة. |
| الخطوة الثانية | بعد كلمة المرور يصدر توكن مؤقت لمدة 5 دقائق لا يصلح جلسةً، والتخمين فيه محدود أيضاً. الإيقاف يحتاج كلمة المرور ورمزاً. |
| الدعوات | المشرف لا يدعو بدور يملك صلاحيات لا يملكها هو. القبول يتطلب الدخول بالبريد المدعو نفسه، والبحث عن الدعوة برابطها يمر عبر دالة `SECURITY DEFINER` لا تكشف غيرها. |
| مفاتيح المرور (Passkeys) | تُضاف من صفحة الحساب بعد إعادة التحقق من كلمة المرور، ويُرسل بريد بإضافتها. الدخول بها بلا كلمة مرور: الجهاز يتحقق من الشخص (بصمة أو وجه أو رمز، `userVerification: required`)، فيُحسب الدخول بخطوتين ولا يُطلب رمز التطبيق. كل عملية بتحدٍّ يُحفظ في الخادم ويُحذف عند أول استخدام فلا يُعاد الرد الملتقَط، والعدّاد الذي يرجع للخلف (نسخة من المفتاح) مرفوض، والمحاولات الفاشلة تدخل حد المحاولات نفسه. الطرف المعتمد هو اسم مضيف التطبيق (`NOVARA_APP_BASE_URL`)، ولا يُحفظ إلا المفتاح العام. حتى 10 مفاتيح لكل حساب. المكتبة: `webauthn` 3.0.1. |
| تغيير طرق الدخول | كل جلسة تعرف هل فُتحت بخطوة ثانية (رمز التطبيق أو مفتاح مرور). إذا كان للحساب خطوة ثانية فإن إضافة مفتاح مرور أو حذفه أو إعداد التطبيق يحتاج جلسة فُتحت بها، لا كلمة المرور وحدها، فلا تستطيع كلمة مرور مسروقة إضافة مفتاحها أو تطبيقها ولا حذف مفتاحك. أول خطوة ثانية تُضاف للحساب تجعل الجلسة التي أُضيفت فيها جلسة بخطوتين. ومن فقد كل مفاتيحه بلا تطبيق يدخل بكلمة المرور إلى المؤسسات التي لا تلزم بالخطوتين فقط. |
| إلزام المؤسسة بالتحقق بخطوتين | من يملك `org.manage` يفرضه على كل الأعضاء، بشرط أن يكون دخوله هو بخطوتين. يتحقق الشرط إذا كان التطبيق مفعّلاً على الحساب (فكل دخول بكلمة المرور يطلب رمزه) أو إذا فُتحت الجلسة بمفتاح مرور. العضو الذي دخل بكلمة المرور وحدها يرى سبب المنع فقط ولا يصل لأي بيانات (403 في الخادم)، ومن لديه مفتاح مرور يجد زر «الدخول بمفتاح مرور» في صفحة المنع نفسها. لا يستطيع العضو حذف آخر خطوة ثانية لديه (التطبيق أو آخر مفتاح مرور) ما دام عضواً في مؤسسة تلزم بها. قائمة الأعضاء تعرض التطبيق أو مفتاح المرور. سير العمل الآلي لا يتأثر. |

إعدادات الإنتاج المتعلقة:

| المتغير | الغرض |
|---|---|
| `NOVARA_ENCRYPTION_KEY` | مفتاح تشفير الأسرار في القاعدة (32 حرفاً على الأقل)، وإلزامي في الإنتاج |

## تخزين الملفات

الافتراضي مجلد على القرص (`NOVARA_STORAGE_ROOT`). لتشغيل أكثر من نسخة من الخادم، أو لفصل الملفات عن الخادم، يُستخدم S3
أو أي خدمة متوافقة معه (MinIO، Cloudflare R2، Wasabi...). الطلبات موقّعة بـ AWS Signature V4، وتوقيعها مُختبر على مثال AWS الرسمي،
والعنوان بصيغة المسار (`endpoint/bucket/key`) فيعمل مع الخدمات التي لا تدعم النطاقات الفرعية. مفاتيح الكائنات تبدأ بمعرّف المؤسسة كما في القرص.

| المتغير | الغرض |
|---|---|
| `NOVARA_STORAGE_BACKEND` | `local` (الافتراضي) أو `s3` |
| `NOVARA_S3_ENDPOINT` | عنوان الخدمة، مثل `https://s3.eu-central-1.amazonaws.com` (https إلزامي في الإنتاج) |
| `NOVARA_S3_BUCKET`, `NOVARA_S3_REGION` | اسم الحاوية والمنطقة (`us-east-1` افتراضيًا، و`auto` لـ Cloudflare R2) |
| `NOVARA_S3_ACCESS_KEY_ID`, `NOVARA_S3_SECRET_ACCESS_KEY` | مفتاح بصلاحيات `GetObject` و`PutObject` و`DeleteObject` على الحاوية فقط |
| `NOVARA_S3_PREFIX` | بادئة اختيارية لكل المفاتيح، لمشاركة حاوية واحدة بين بيئات |

الخادم يرفض أن يبدأ إذا اختير `s3` دون الحاوية أو المفاتيح.


## الإنتاج خلف nginx

`infrastructure/deployment/nginx.conf` هو الباب الأمامي: التطبيق والـ API على أصل واحد، مع حدود لكل عنوان قبل أن يصل الطلب إلى Python:

| المسار | الحد لكل عنوان |
|---|---|
| `/api/v1/auth/` (الدخول والتسجيل والاستعادة) | 10 في الدقيقة، ودفعة 10 |
| `/api/v1/public/` و`/api/v1/hooks/` (المواقع المنشورة والأنظمة الأخرى) | 120 في الدقيقة، ودفعة 60 |
| بقية `/api/` | 20 في الثانية، ودفعة 80 |
| التحديثات الحية (SSE) | 10 اتصالات مفتوحة |

تجاوز الحد يرجع 429 بجسم JSON و`Retry-After: 60`، كما يفعل الـ API. هذه الحدود أمام حدود الـ API نفسه (لكل بريد، ولكل مفتاح، ولكل سير عمل) ولا تُغني عنها.

**عنوان المستخدم:** يرسل nginx عنوان الاتصال الحقيقي في `X-Forwarded-For`، ويثق uvicorn بهذا الرأس من `127.0.0.1` فقط (الافتراضي: `--proxy-headers --forwarded-allow-ips 127.0.0.1`). لا تضبط `--forwarded-allow-ips '*'` أبداً، وإلا استطاع أي أحد ادعاء أي عنوان وتجاوز الحدود. إن كان أمام nginx موازن أحمال، فاستخدم `set_real_ip_from` و`real_ip_header` ليكون `$remote_addr` هو الزائر لا الموازن.
